# 아이디어 발굴 (idea-mining)

이 스킬은 "아이디어를 뿜어내는" 것보다 "검증 가능한 문제-해법 쌍을 남기는" 것을 목표로 한다. 발산만 하고 끝나면 대화가 끝나자마자 사라지고, 다음에 또 같은 걸 다시 고민하게 된다. 그래서 이 스킬은 매번 같은 절차(문제 발굴 → 해법 발산 → 점수로 수렴 → 파일로 저장)를 따르고, 결과를 `~/ideas/`에 누적해서 다음 세션에서도 이어 쓸 수 있게 한다.

## 이 스킬을 언제 쓰지 않는가

이미 무엇을 만들지 정해진 상태에서 그것을 어떻게 구현할지 설계하는 요청, 단순 네이밍, 카피 한 줄 뽑기 같은 작업에는 이 스킬을 쓰지 않는다. 이 스킬은 "무엇을 할지"가 아직 정해지지 않은 단계를 위한 것이다.

## 두 가지 모드

1. **발굴 모드** (기본): 새로운 아이디어를 찾는다. 아래 워크플로를 따른다.
2. **조회/관리 모드**: "예전 아이디어 뭐 있었지", "아이디어 목록 보여줘", "그 아이디어 상태 바꿔줘" 같은 요청. 새로 발굴하지 말고 `~/ideas/INDEX.md`를 읽어 답한다. 상태 변경은 해당 아이디어 파일의 frontmatter와 INDEX.md를 함께 갱신한다. `~/ideas/`가 아직 없으면 "아직 쌓인 아이디어가 없다"고 안내하고 발굴 모드로 전환할지 물어본다.

## 발굴 모드 워크플로

전체 흐름: **0. 스코핑 → 1. 문제 발굴 → (체크포인트 A) → 2. 해법 발산 → 3. 수렴 → (체크포인트 B) → 4. 저장**

사용자가 "그냥 알아서 진행해"라고 하면 체크포인트를 건너뛰고, 대신 결과물 상단에 어떤 가정으로 진행했는지 명시한다. 절차가 목적이 아니라 좋은 결과물이 목적이므로, 대화 맥락에 이미 답이 있는 항목은 다시 묻지 않는다.

### 0단계: 스코핑

`AskUserQuestion`으로 한 번에 파악한다 (이미 알고 있는 항목은 생략):

- **영역**: 신규 사업/서비스, 기존 제품 기능/개선, 기술 실험/사이드 프로젝트, 콘텐츠·마케팅 중 무엇인가 (복수 선택 가능)
- **재료 소스**: 웹 리서치, 사용자의 메모/문서 폴더, 현재 코드베이스, 모델 지식 중 무엇을 쓸지 — 자세한 실행 방법은 `references/sources.md` 참고
- **제약**: 가용 시간, 예산, 보유 기술/역량, 이미 제외하고 싶은 방향
- **성공 기준**: 이번 세션에서 뭘 얻으면 만족인가 (예: "바로 시작할 만한 것 1개" vs "폭넓게 훑어보고 싶다")

### 1단계: 문제 발굴 (체크포인트 A로 마무리)

선택된 재료 소스에서 페인포인트를 8~15개 찾는다. 소스별 수집 방법은 `references/sources.md`를 읽고 따른다. 여러 소스를 동시에 쓸 때는 병렬로 수집하고, 두 소스 이상에서 겹치는 신호를 우선순위로 올린다.

각 문제는 반드시 아래 5개 필드를 채운다. 이걸 강제하는 이유는, 필드가 비어 있으면 그 문제가 실재하는지 그냥 그럴듯하게 들리는 것뿐인지 구분이 안 되기 때문이다.

- **누가**: 구체적인 사람/역할. "사용자들"이 아니라 "월 100건 이하 처리하는 1인 세무사"처럼.
- **언제**: 문제가 발생하는 실제 상황과 빈도
- **왜 아픈가**: 시간/돈/리스크 중 무엇으로 손해를 보는가
- **지금은 어떻게 버티나**: 현재 쓰는 우회법. 아무 우회법도 없다면 그 문제가 사실 별로 안 아프다는 신호일 수 있다.
- **왜 아직 안 풀렸나**: 기술적으로 어려워서인지, 규제 때문인지, 유통/채널이 없어서인지, 아니면 그냥 아무도 안 만들어서인지

목록을 만든 뒤 `AskUserQuestion`으로 **체크포인트 A**: 이 중 어떤 문제 1~3개를 깊게 팔지 사용자에게 고르게 한다.

### 2단계: 해법 발산 (평가하지 않는다)

선택된 문제마다 5~8개의 해법을 낸다. 이 단계에서는 좋고 나쁨을 판단하지 않는다 — 평가는 3단계에서 한다. 발산 중에 스스로 걸러내기 시작하면 뻔한 아이디어만 남는다.

같은 방향으로만 쏠리는 걸 막기 위해 최소 4개의 서로 다른 각도를 강제로 배정한다:
- 기존 대체재를 훨씬 더 좋게 (10배 개선)
- 다른 사용자층으로 옮기기 (같은 해법, 다른 대상)
- 사람이 수동으로 하던 걸 자동화
- 번들을 쪼개거나, 반대로 흩어진 걸 하나로 묶기
- 지금까지 이 문제를 아예 안 겪던 사람(비소비자)을 새 사용자로 끌어들이기

### 3단계: 수렴 (체크포인트 B로 마무리)

`references/scoring.md`의 루브릭으로 각 해법에 점수를 매긴다. 문제 우선 접근이므로 문제 강도에 가중치를 둔다.

상위 3~5개에는 반드시 다음 셋을 붙인다 — 점수만 있고 이게 없으면 아이디어가 아니라 그냥 감상이다:
1. **가장 위험한 가정**: 이게 틀리면 전체가 무너지는 지점
2. **최소 검증 실험**: 그 가정을 1주 안에 확인할 가장 싼 방법
3. **kill 조건**: 무엇을 확인하면 접을지

정리된 상위안을 보여주고 `AskUserQuestion`으로 **체크포인트 B**: 어떤 걸 `~/ideas/`에 저장할지 확정한다 (전부 저장도 가능).

### 4단계: 저장

`references/templates.md`의 포맷을 따른다.

1. `~/ideas/`가 없으면 이때 생성한다 (스킬 자체에는 이 폴더가 없다 — 첫 사용 시 새로 만드는 것).
2. **저장 전에 반드시 `~/ideas/INDEX.md`를 먼저 읽고** 확정된 아이디어와 비슷한 게 이미 있는지 확인한다. 있으면 새 파일을 만들지 않고 기존 파일에 "재발견 / 새 근거" 섹션을 추가한다. 이렇게 하지 않으면 같은 아이디어가 슬러그만 바뀐 채 여러 파일로 흩어지고, 목록이 관리 도구가 아니라 쓰레기장이 된다.
3. 새 아이디어는 `~/ideas/YYYY-MM-DD-<slug>.md`로 저장한다 (frontmatter: `id`, `title`, `domain`, `status`(기본 `inbox`), `score`, `created`, `source`, `problem`).
4. `~/ideas/INDEX.md`를 갱신한다 — 상태별로 묶은 표.
5. 탈락한 해법을 포함한 세션 전체 기록을 `~/ideas/sessions/YYYY-MM-DD-<topic>.md`에 남긴다. 오늘 버린 아이디어가 몇 달 뒤엔 맞는 답이 되는 경우가 흔하므로 버린 것도 보존한다.

저장이 끝나면 사용자에게 저장된 파일 경로와 각 아이디어의 다음 행동(최소 검증 실험)을 간단히 요약해 알려준다.

## 품질 기준

1. **구체성**: 주어 없는 아이디어("AI로 X를 개선한다")는 통과시키지 않는다. 누가, 언제, 무엇 때문에 곤란한지가 없으면 나중에 검증할 방법이 없다.
2. **정직성**: 웹 리서치로 확인한 사실과 모델의 추정을 문서에서 시각적으로 구분한다(예: "확인됨" vs "추정"). 섞이면 나중에 이 문서만 보고 잘못된 판단을 내리게 된다.
3. **개수보다 밀도**: 20개를 얕게 나열하는 것보다 상위 몇 개를 검증 가능한 수준까지 파는 것이 이 스킬의 목적이다.

## 참고 파일

- `references/sources.md` — 재료 소스별(웹/메모/코드베이스/모델 지식) 구체적인 수집 방법
- `references/scoring.md` — 스코어링 루브릭과 가정/실험/kill 조건 작성 예시
- `references/templates.md` — 아이디어 파일, INDEX.md, 세션 로그의 실제 작성 예시
