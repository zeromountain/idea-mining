# 아이디어 발굴 (idea-mining)

이 스킬은 "아이디어를 뿜어내는" 것보다 "검증 가능한 문제-해법 쌍을 남기는" 것을 목표로 한다. 발산만 하고 끝나면 대화가 끝나자마자 사라지고, 다음에 또 같은 걸 다시 고민하게 된다. 그래서 이 스킬은 매번 같은 절차를 따르고, 결과를 `~/ideas/`에 누적해서 다음 세션에서도 이어 쓸 수 있게 한다.

## 이 스킬을 언제 쓰지 않는가

이미 무엇을 만들지 정해진 상태에서 그것을 어떻게 구현할지 설계하는 요청, 단순 네이밍, 카피 한 줄 뽑기 같은 작업에는 이 스킬을 쓰지 않는다. 이 스킬은 "무엇을 할지"가 아직 정해지지 않은 단계를 위한 것이다.

## 세 가지 모드

1. **빠른 모드** (기본): 가볍게 훑어본다. 서브에이전트를 쓰지 않고, 도메인 방법론 중 필수 질문과 흔한 실패 패턴만 적용한다.
2. **깊은 모드**: "제대로", "깊게", "본격적으로", "리서치해서" 같은 표현이 있거나 0단계 스코핑에서 사용자가 직접 고르면 진입한다. 병렬 리서치(문제 공간 지도 포함), 3갈래 기존 해결책 판정, 독립 비평, 도메인 방법론 전체를 적용한다.
3. **조회/관리 모드**: 새로 발굴하지 않고 `~/ideas/`를 다룬다. `references/portfolio.md`를 따른다.

빠른 모드로 먼저 훑고, 결과를 보여준 뒤 "이 중 하나를 깊게 파볼지" 제안하는 흐름이 자연스럽다 — 처음부터 무겁게 시작하는 것보다 실제 사용 패턴에 맞는다. 사용자가 "그냥 알아서 진행해"라고 하면 어느 모드든 체크포인트를 건너뛰고, 대신 결과물 상단에 어떤 가정으로 진행했는지 명시한다.

## 발굴 워크플로

전체 흐름: **0. 스코핑 → 1. 문제 발굴 → (체크포인트 A) → 2. 해법 발산 → 3. 비평 → 4. 수렴 → (체크포인트 B) → 5. 저장**

각 단계에서 무엇을 읽고 무엇을 하는지는 아래에 정리한다. `[깊은 모드]`라고 표시된 부분은 깊은 모드에서만 하고, 표시 없는 내용은 두 모드 공통이다.

### 0단계: 스코핑

`AskUserQuestion`으로 한 번에 파악한다 (이미 알고 있는 항목은 생략):

- **영역**: 신규 사업/서비스, 기존 제품 기능/개선, 기술 실험/사이드 프로젝트, 콘텐츠·마케팅 중 무엇인가 (복수 선택 가능). 이 답으로 이후 단계에서 읽을 `references/domains/<domain>.md`가 정해진다 — business/product/tech/content 중 해당하는 파일.
- **재료 소스**: 웹 리서치, 사용자의 메모/문서 폴더, 현재 코드베이스, 모델 지식 중 무엇을 쓸지 — 자세한 실행 방법은 `references/sources.md` 참고
- **제약**: 가용 시간, 예산, 보유 기술/역량, 이미 제외하고 싶은 방향
- **성공 기준**: 이번 세션에서 뭘 얻으면 만족인가
- **모드**: 대화 맥락에 이미 신호가 없으면 빠른/깊은 모드 중 선택지로 제시

### 1단계: 문제 발굴 (체크포인트 A로 마무리)

선택된 재료 소스에서 페인포인트를 8~15개 찾는다. `references/sources.md`를 읽고 따른다. `[깊은 모드]` 소스를 2개 이상 쓸 때는 소스별로 서브에이전트를 병렬로 띄워 동시 수집한다(`Agent` 도구, `sources.md`의 병렬 수집 절차 참고). 이때 각 문제마다 이미 존재하는 대표 해결책도 함께 수집해 **문제 공간 지도**를 만든다(`references/evidence.md`) — 이 지도를 2·3단계에서 재사용하므로 별도로 다시 조사하지 않는다. 빠른 모드는 직접 순차 수집하고 지도는 만들지 않는다.

각 문제는 반드시 아래 5개 필드를 채운다. 필드가 비어 있으면 그 문제가 실재하는지 그럴듯하게 들리는 것뿐인지 구분이 안 되기 때문이다.

- **누가**: 구체적인 사람/역할. "사용자들"이 아니라 "월 100건 이하 처리하는 1인 세무사"처럼.
- **언제**: 문제가 발생하는 실제 상황과 빈도
- **왜 아픈가**: 시간/돈/리스크 중 무엇으로 손해를 보는가
- **지금은 어떻게 버티나**: 현재 쓰는 우회법. 없다면 문제가 사실 별로 안 아프다는 신호일 수 있다.
- **왜 아직 안 풀렸나**: 기술적 난이도, 규제, 유통/채널 부재, 아니면 그냥 아무도 안 만들어서인지

각 근거에는 `references/evidence.md`의 증거 등급(E1/E2/E3)을 표기한다. "왜 아픈가"의 근거가 E3뿐이면 그 문제를 "신뢰도 낮음"으로 표시한다.

`references/domains/<domain>.md`의 "필수 질문"에 답하지 못하는 문제는 이 시점에서 걸러낸다.

목록을 만든 뒤 `AskUserQuestion`으로 **체크포인트 A**: 이 중 어떤 문제 1~3개를 깊게 팔지 사용자에게 고르게 한다. `[깊은 모드]` 각 문제에 문제 공간 지도의 포화도 태그(예: "경쟁 다수"/"소수"/"안 보임")를 함께 보여준다.

### 2단계: 해법 발산 (평가하지 않는다)

`[깊은 모드]` 발산 직전, 문제 공간 지도에 있는 대표 해결책들을 발산의 **제약**으로 준다 — "이미 X·Y·Z 형태가 있다, 같은 형태는 내지 마라". 필터로 뒤늦게 거르기보다 애초에 재발명 방향으로 덜 나오게 하는 게 목적이다.

선택된 문제마다 5~8개의 해법을 낸다. `references/divergence.md`의 기법 중 **최소 3개를 서로 다르게** 배정한다. 이 단계에서는 좋고 나쁨을 판단하지 않는다 — 평가는 3~4단계에서 한다.

발산 후 해법마다 문제 공간 지도와 대조한다(`[깊은 모드]` 전체 해법 필수, 빠른 모드는 3단계에서 상위안이 추려진 뒤 그 상위안만). `references/evidence.md`의 **3갈래 판정**(재발명/세그먼트 협소화/진짜 공백)을 적용한다 — 경쟁자가 있다고 무조건 기각하지 않되, 재발명으로 판정되면 통과시키지 않는다. 이게 뻔한 재발명을 거르는 가장 강한 필터다.

### 3단계: 비평 (점수를 매기기 전에)

`references/critique.md`를 따른다:
- **프리모템**은 두 모드 공통 — "6개월 뒤 실패했다"고 단정하고 원인 5개를 역산한다. `references/domains/<domain>.md`의 "흔한 실패 패턴"을 우선 점검한다.
- **독립 레드팀**은 `[깊은 모드]`만: 서브에이전트에게 아이디어 요약 + 문제 정의 + 도메인 흔한 실패 패턴만 넘기고, 어떻게 도출됐는지 생성 맥락은 넘기지 않는다. "옹호하지 말고 죽여라, 주장마다 증거 등급을 표기하라"라고 명확히 지시한다.
- 반박이 치명적이면 killed로 처리한다. 단, 근거가 E3(추론)뿐이면 검색 1회로 승격을 시도하고 실패하면 부분적으로 강등한다. **killed로 확정되면 아이디어 파일을 만들지 않는다** — 세션 로그에 남기고 `INDEX.md` killed 표에 사유와 세션 로그 링크만 한 줄 추가한다(`portfolio.md`의 저장 이후 kill과는 다른 경로).
- 부분적이면 가정을 수정하고 4단계로. **해법 형태가 실질적으로 바뀌었다면(피벗) `references/evidence.md`로 돌아가 문제 공간 지도 대조를 다시 한 뒤** 4단계로 넘어간다.
- 반박을 견디면 그대로 4단계로.
- **라운드 전멸 가드** `[깊은 모드]`: 한 라운드(발산~비평)에서 후보가 하나도 안 남으면 즉시 `AskUserQuestion`으로 4지선다(발산 각도 변경 / 다른 문제 / 영역 전환 / 제약 완화)를 묻는다(`critique.md` §5). "알아서 진행해" 모드에서는 발산 각도 변경을 1회 자동 시도 후 그래도 전멸하면 보고하고 멈춘다.

### 4단계: 수렴 (체크포인트 B로 마무리)

`references/scoring.md`의 공통 4항목(문제 강도 ×2, 본인 적합도, 검증 속도, 차별성)으로 점수를 매긴다. `references/domains/<domain>.md`의 "추가 점수 항목"도 더한다 — `[깊은 모드]`는 전체 후보에 필수, 빠른 모드는 상위 후보에만. 점수와 별개로 후보들 간 **강제 순위**를 매긴다(`scoring.md` 참고, 자기채점 편향 완화 목적).

상위 3~5개에는 반드시 다음 셋을 붙인다 — 점수만 있고 이게 없으면 아이디어가 아니라 감상이다:
1. **가장 위험한 가정**: 이게 틀리면 전체가 무너지는 지점
2. **최소 검증 실험**: 그 가정을 1주 안에 확인할 가장 싼 방법 (도메인별 예시는 `references/domains/<domain>.md` 참고)
3. **kill 조건**: 무엇을 확인하면 접을지

정리된 상위안을 보여주고 `AskUserQuestion`으로 **체크포인트 B**: 어떤 걸 `~/ideas/`에 저장할지 확정한다.

### 5단계: 저장

`references/templates.md`의 포맷을 따른다.

1. `~/ideas/`가 없으면 이때 생성한다 (스킬 자체에는 이 폴더가 없다 — 첫 사용 시 새로 만드는 것).
2. **저장 전에 반드시 `~/ideas/INDEX.md`를 먼저 읽고** 확정된 아이디어와 비슷한 게 이미 있는지 확인한다. 있으면 새 파일을 만들지 않고 기존 파일에 "재발견 / 새 근거" 섹션을 추가한다.
3. 새 아이디어는 `~/ideas/YYYY-MM-DD-<slug>.md`로 저장한다 (frontmatter: `id`, `title`, `domain`, `status`(기본 `inbox`), `score`, `created`, `source`, `problem`, `review_after`(기본 `null`)). 본문에는 문제, 기존 대안(3갈래 판정 포함), 해법, **비평**(프리모템+독립 레드팀 요약+반영 판단, 레드팀 주장을 검증했다면 그 결과 포함), 스코어, 검증 계획, 빈 실험 로그 표를 포함한다.
4. `~/ideas/INDEX.md`를 갱신한다 — 상태별로 묶은 표. 3단계에서 파일 없이 killed된 항목도 killed 표에 사유·세션 로그 링크로 등록한다.
5. 탈락한 해법을 포함한 세션 전체 기록을 `~/ideas/sessions/YYYY-MM-DD-<topic>.md`에 남긴다 (문제 공간 지도·발산 기법·비평 결과 포함). 오늘 버린 아이디어가 몇 달 뒤엔 맞는 답이 되는 경우가 흔하므로 버린 것도 보존한다.

저장이 끝나면 사용자에게 저장된 파일 경로와 각 아이디어의 다음 행동(최소 검증 실험)을 간단히 요약해 알려준다.

## 조회/관리 모드

`references/portfolio.md`를 따른다. 새로 발굴하지 않고 `~/ideas/INDEX.md`와 개별 파일을 읽어 답한다.

- **목록/조회**: 상태별로 정리해 보여준다.
- **상태 변경**: 해당 파일의 frontmatter `status`와 `INDEX.md`를 함께 갱신한다. `parked`로 옮길 때는 `review_after` 날짜를 반드시 받는다.
- **검증 결과 보고**: 사용자가 실험 결과를 알려주면 해당 파일의 실험 로그 표에 한 줄 추가하고 상태를 갱신한다.
- **점검 요청** ("아이디어 점검해줘"): `inbox` 90일 경과, `exploring`인데 실험 로그 비어 있음, `parked` 재검토일 경과를 지적하고, 뚜렷한 테마 클러스터가 보이면 짚어준다.
- `~/ideas/`가 아직 없으면 "아직 쌓인 아이디어가 없다"고 안내하고 발굴 모드로 전환할지 물어본다.

## 품질 기준

1. **구체성**: 주어 없는 아이디어("AI로 X를 개선한다")는 통과시키지 않는다. 누가, 언제, 무엇 때문에 곤란한지가 없으면 나중에 검증할 방법이 없다.
2. **정직성**: 증거 등급(E1/E2/E3, `references/evidence.md`)을 문서에 항상 표기한다. 확인된 사실과 추정이 섞이면 나중에 이 문서만 보고 잘못된 판단을 내리게 된다.
3. **반박 우선**: 점수를 매기기 전에 항상 비평 단계(`references/critique.md`)를 거친다. 반박 없이 매긴 점수는 후하게 나오기 마련이다.
4. **개수보다 밀도**: 20개를 얕게 나열하는 것보다 상위 몇 개를 검증 가능한 수준까지 파는 것이 이 스킬의 목적이다.

## 참고 파일
