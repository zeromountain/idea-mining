# 축적·후속 관리 (조회/관리 모드)

발굴은 시작일 뿐이다. 검증 실험을 적어두고 결과를 기록할 곳이 없으면 아이디어는 `inbox`에 방치된 채 쌓이기만 한다. 이 파일은 저장 이후의 흐름을 다룬다.

## 실험 로그

아이디어 파일마다 아래 표를 유지한다 (`templates.md`의 예시 참고):

| 날짜 | 가설 | 실행한 것 | 결과 | 결정 |
|---|---|---|---|---|
| ... | 검증하려던 가정 | 실제로 한 행동 | 관찰된 결과 | 계속/수정/폐기 |

사용자가 "이 아이디어 검증해봤는데" 같은 말로 결과를 알려주면, 해당 아이디어 파일을 찾아 이 표에 한 줄 추가하고 `status`를 갱신한다. 새 정보 없이 그냥 기록만 요청받으면 새 파일을 만들지 않고 기존 파일을 갱신한다.

## 상태 전이 규칙

- `inbox` → `exploring`: 최소 검증 실험을 실제로 시작했을 때
- `exploring` → `building`: kill 조건을 통과하고 실행하기로 결정했을 때
- `exploring` → `killed`: kill 조건이 충족됐을 때. **사유를 실험 로그에 반드시 남긴다.** 이 경로는 아이디어 파일이 이미 존재하는 상태에서 상태만 바뀌는 것이다 — 파일을 지우지 않는다.
- **비평 단계(발굴 워크플로 3단계)에서 치명적 반박으로 죽는 경우는 이것과 다르다.** 그때는 애초에 아이디어 파일을 만들지 않으므로 상태 전이가 아니다 — 세션 로그에 남기고 `INDEX.md`의 killed 표에 제목·영역·킬 사유·세션 로그 링크만 한 줄 추가한다 (`critique.md` 반영 규칙, `templates.md` 참고).
- `exploring`/`inbox` → `parked`: 지금은 안 하지만 완전히 접은 건 아닐 때. **보류 사유와 재검토 날짜를 frontmatter에 필수로 남긴다** (예: `review_after: 2026-11-01`). 날짜 없이 보류하면 사실상 방치와 같다.

## 방치 감지

조회 모드("아이디어 점검해줘", "아이디어 목록 보여줘")에서 `~/ideas/INDEX.md`와 각 파일을 훑어 아래를 지적한다:

- `inbox` 상태로 90일 넘게 머문 아이디어 — 검증을 시작할지, 접을지 사용자에게 묻는다
- `exploring` 상태인데 실험 로그가 비어 있는 아이디어 — 상태만 바뀌고 실제 검증은 없었다는 신호
- `parked`인데 `review_after` 날짜가 지난 아이디어 — 재검토 시점이 됐음을 알린다

파일 없이 killed된 항목(비평 단계에서 죽어 세션 로그에만 있는 것)은 애초에 파일이 없으므로 위 감지 대상이 아니다 — INDEX의 killed 표는 그대로 기록으로만 남긴다.

## 테마 클러스터링

여러 아이디어를 훑다 보면 반복되는 주제나 관심사가 보일 수 있다 (예: 저장된 아이디어 중 다수가 "소규모 자영업자의 수작업 자동화"). 조회 모드에서 이런 패턴이 눈에 띄면 짚어준다 — 사용자 본인의 관심사 패턴을 알면 다음 발굴 세션의 0단계 스코핑이 더 정확해진다. 근거 없이 무리하게 클러스터링을 시도하지 말고, 뚜렷한 반복이 보일 때만 언급한다.
