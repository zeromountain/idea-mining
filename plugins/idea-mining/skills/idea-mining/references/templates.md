# 소규모 세무사무소용 거래 자동분류 정확도 개선 도구

## 문제
- **누가**: 월 100건 이하 처리하는 1인·소규모 세무사무소
- **언제**: 매월 마감 시 거래 내역을 회계 SW에서 불러온 직후
- **왜 아픈가**: 잘못 분류된 항목을 하나하나 재확인하느라 건당 10~15분 추가 소요, 월 15~20시간
- **지금은 어떻게 버티나**: 엑셀에 규칙을 따로 만들어 수작업 대조
- **왜 아직 안 풀렸나**: 대형 회계 SW는 대량 고객 대상 범용 모델이라 업종별 미세조정을 안 함

(E1, 출처: https://example.com/review-thread, 확인일 2026-08-05) 관련 커뮤니티 스레드에서 동일 불만 다수 발견 — "매달 30건 넘게 손으로 다시 고친다"는 원문 인용.
(E3) 소규모 사무소일수록 업종이 몰려 있어 미세조정 여지가 클 것으로 보임 — 미검증 추론.

## 기존 대안
- **A사 회계 SW의 자동분류**: 이미 쓰고 있는 것 자체. 범용 모델이라 업종별 정확도가 낮음 — 충분하지 않은 이유. **판정: 세그먼트 협소화** (차별성 점수 상한 3점 적용)
- **B 서비스(범용 규칙 엔진)**: 규칙을 직접 짜야 해서 비개발자인 세무사에게 진입장벽이 높음 — 충분하지 않은 이유. **판정: 세그먼트 협소화**

## 해법 (선택된 것)
기존 회계 SW에 플러그인으로 붙는, 업종별 규칙 학습형 분류 보조 도구.

## 비평

### 프리모템
- 세무사가 기존 SW를 바꾸지 않고 플러그인만 추가로 신뢰하지 않을 위험 → 기존 SW 안에서 동작하는 형태로 완화
- 업종별 규칙이 실제로는 사무소마다 달라 일반화가 안 될 위험 → 최소 검증 실험에서 확인 예정

### 독립 레드팀 (서브에이전트, 맥락 차단)
- (E2) "업종별 회계 처리는 지역·업종 표준이 이미 있어 규칙 일반화가 생각보다 쉬울 수 있다"는 반박을 제시
- (E3) "세무사들이 플러그인 형태 자체를 신뢰하지 않을 것"이라는 추가 반박

### 반영
- **레드팀 주장 → 검증 결과**: 위 E2 주장의 원 출처를 검색했으나 확인 못 함 → **E3로 강등**. 근거가 흔들려 반박 강도를 하향 조정.
- **판정**: 부분적 반박. "완전 자동화"였던 원래 가정을 "업종별 반자동 규칙 제안(사람이 최종 확인)"으로 수정. 해법의 형태 자체는 바뀌지 않아 `evidence.md` 재대조는 생략.

`## 기획 문서` 섹션은 기획을 실제로 시작하기 전에는 존재하지 않는다 — 기존 아이디어 파일을 소급해서 이 섹션으로 채우지 않는다. `01-prd.md`가 만들어지는 시점에 한 번 추가하고, 이후 문서가 늘어날 때마다 표의 `상태`만 갱신한다.

이 예시는 `## 실험 로그`가 비어 있는데도 `status: building`인 상태를 보여준다 — 검증을 건너뛰고 기획 모드로 바로 들어간 경우다(`planning.md` 2단계 검증 게이트). 이런 경우 `01-prd.md`에는 "미검증 가정 위에서 시작한 기획"이라는 표시가 반드시 있어야 한다. 실험을 먼저 마치고 `exploring` 상태에서 `building`으로 넘어온 경우라면 `## 실험 로그`에 최소 한 줄이 있어야 정상이다.

`review_after`는 `status: parked`일 때만 실제 날짜(`YYYY-MM-DD`)를 채운다. 그 외 상태에서는 `null`로 둔다.

`기획` 컬럼은 기획 모드로 착수한 아이디어에만 채운다 — 나머지는 `—`로 둔다. 기획 문서는 아이디어와 다른 위치(사용자가 작업 중인 프로젝트 폴더)에 있으므로 이 컬럼의 값은 `~/ideas/` 기준 상대경로가 아니라 절대경로 또는 프로젝트를 알아볼 수 있는 경로 표기를 쓴다. `killed` 표는 컬럼을 늘리지 않는다 — 기획까지 갔던 항목이 죽으면 `사유` 뒤에 `(기획 문서: <경로>)`를 괄호로 덧붙인다.

killed 표의 `파일` 컬럼은 두 종류를 구분해서 채운다: 저장된 뒤 kill 조건 충족으로 죽은 경우는 그 아이디어 파일 링크를, 비평 단계에서 애초에 파일 없이 죽은 경우는 세션 로그 링크를 넣는다 (`critique.md` 반영 규칙, `portfolio.md` 참고). `사유` 컬럼은 후자의 경우 특히 중요하다 — 파일이 없으므로 이 한 줄이 유일한 기록이고, 같은 아이디어가 나중에 다시 나왔을 때 왜 죽었는지 여기서만 확인할 수 있다.

## 기획 문서 (`<프로젝트 루트>/docs/planning/<idea-slug>/`)

# PRD: 소규모 세무사무소용 거래 자동분류 정확도 개선 도구

> **미검증 가정 위에서 시작한 기획**: 이 아이디어는 아직 `status: inbox`이고 실험 로그가 비어 있다 — "세무사가 이 불편 때문에 실제로 별도 유료 도구를 도입할 의향이 있다"는 가장 위험한 가정이 검증되지 않은 채로 기획을 진행한다. 검증 계획대로 인터뷰 5명을 먼저 진행하는 것을 권장한다.

## 배경
월 100건 이하 처리하는 1인·소규모 세무사무소가 기존 회계 SW의 자동 분류 정확도(~80%)를 매달 수작업으로 재검토하며 월 15~20시간을 쓰고 있다 (`~/ideas/2026-08-05-tax-autocategorize.md` 참고).

## 문제
- **누가**: 월 100건 이하 처리하는 1인·소규모 세무사무소
- **언제**: 매월 마감 시 거래 내역을 회계 SW에서 불러온 직후
- **왜 아픈가**: 잘못 분류된 항목 재확인에 건당 10~15분, 월 15~20시간 소요

## 목표 / 비목표
- **목표**: 기존 회계 SW 위에서 동작하는 업종별 규칙 학습형 분류 보조로 재검토 시간을 50% 이상 줄인다
- **비목표**: 회계 SW 자체를 대체하지 않는다. 완전 자동화(사람 확인 없는 분류 확정)는 하지 않는다 — 비평 단계에서 이 가정이 "완전 자동화"에서 "반자동 규칙 제안"으로 이미 수정됨(아이디어 파일 `## 비평` > `## 반영` 참고)

## 타깃 사용자
월 100건 이하 처리하는 1인·소규모 세무사무소 (페르소나: 세무사 본인이 직접 회계 SW를 조작하는 경우, 별도 전산 담당자 없음)

## 성공 지표
- 재검토 시간 월 15~20시간 → 7~10시간 이하로 감소 (검증 계획의 최소 검증 실험 결과와 함께 갱신 예정)

## 범위
- **MVP**: 업종별 규칙 제안 + 사람 확인 UI
- **차기**: 규칙 자동 학습(사무소별 히스토리 기반)
- **제외**: 완전 자동 확정, 신규 회계 SW 자체 개발

## 리스크 (아이디어 파일 비평에서 승계)
- 세무사가 기존 SW를 바꾸지 않고 플러그인만 추가로 신뢰하지 않을 위험 → 완화책: 기존 SW 안에서 동작
- (E2 → E3로 강등, 미검증) 업종별 규칙이 사무소마다 달라 일반화가 안 될 위험 — 최소 검증 실험에서 확인 필요

# 핵심 플로우

## 플로우: 월간 마감 분류 재검토 (MVP 기능만 대상)
1. 세무사가 회계 SW에서 거래 내역을 불러온다 (기존 SW 화면, 변경 없음)
2. 도구가 회계 SW의 분류 결과를 읽어 신뢰도 낮은 항목에 업종별 대안 분류를 제안한다
3. 세무사가 제안을 승인/거부/수정한다
4. 거부·수정 이력이 다음 달 규칙 제안에 반영된다 (차기 기능과 연결되는 지점, MVP에서는 로그만 축적)

- 업종이 등록되지 않은 신규 고객 거래 → 제안 없이 원래 회계 SW 분류 그대로 통과
- 제안 신뢰도가 너무 낮음 → 제안 자체를 표시하지 않음 (거짓 확신 방지)

# 기술 설계

## 아키텍처 개요
회계 SW를 대체하지 않는 애드온 형태 — 거래 내역을 읽어 제안을 생성하고, 승인/거부 결과를 다시 축적하는 단방향 파이프라인.

## 주요 컴포넌트
- 내보내기 파일 파서 (회계 SW가 API를 안 열어줄 가능성이 높아 파일 기반을 기본으로 가정 — 미검증)
- 규칙 매칭 엔진 (IndustryRule 대조)
- 확인 UI (웹 또는 스프레드시트 애드인 — 미정)

## 미해결 기술 리스크
- 회계 SW 대상을 1개로 좁힐지 여러 개로 갈지 (04-data-model의 외부 연동 미정 항목과 연결)
- 신뢰도 낮은 제안을 숨기는 임계값을 어떻게 정할지 (초기엔 규칙 기반, 이후 사용 데이터로 튜닝)
