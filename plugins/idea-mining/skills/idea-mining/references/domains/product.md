# 도메인: 기존 제품 기능/개선

이미 사용자가 있는 제품에 뭘 더할지 판단하는 것이므로, 새로 사람을 모으는 게 아니라 **기존 사용자 중 얼마나 많은 비율에 실제로 영향을 주는가**가 핵심이다.

## 필수 질문

- **안 만들면 무슨 일이 생기나**: 지금처럼 안 만들어도 사용자가 계속 쓰는가, 아니면 이탈·불만이 누적되는가. 답이 "딱히 문제없다"면 우선순위가 낮다는 신호다.
- **전체 사용자 중 몇 %에 영향**: 요청한 사람이 소수라도, 그 소수가 전체를 대표하는지 아니면 목소리만 큰 예외인지 구분한다.
- **제품 안에 이미 우회법이 있나**: 지금도 다른 기능을 조합해서 어떻게든 되고 있다면, 그 우회가 얼마나 불편한지가 실제 우선순위다.

## 추가 점수 항목 (공통 4항목에 더함, `scoring.md` 참고)

- **RICE 스코어**: Reach(영향받는 사용자 수/비율) × Impact(1인당 개선 체감도, 1~3) × Confidence(추정 신뢰도, %) ÷ Effort(공수, 사람-주). 절대값보다 **다른 후보와의 상대 순위**로 쓴다.
- **기존 기능과의 충돌·카니발라이제이션**: 이미 있는 기능의 사용을 대체하거나 잠식하는지, 아니면 순증인지
- **로드맵 적합성**: 제품이 가려는 방향(있다면)과 같은 축인지, 곁가지인지

## 흔한 실패 패턴 (비평 단계 체크리스트)

- **목소리 큰 소수 사용자**: 문의·리뷰에 자주 등장하지만 전체 사용자 대비 극소수인 요청을 과대평가
- **기능 부풀리기**: 문제 하나에 옵션·설정을 잔뜩 붙여 해결하려 함 — 단순한 해법을 먼저 검토했는지 확인
- **성공 지표 없이 추가**: 이 기능이 성공했는지 무엇으로 판단할지 미리 정하지 않음
- **경쟁사 기능 따라잡기**: "저쪽에 있으니까"가 유일한 근거이고 자사 사용자에게 왜 필요한지 설명이 없음

## 최소 검증 실험 예시

- 기존 사용자 대상 짧은 설문/투표로 수요 확인
- 페이크 도어(가짜 버튼/링크)를 넣어 클릭률로 관심도 측정
- 헤비유저 3~5명과 사용성 인터뷰
- 기능 대신 수동 프로세스(컨시어지)로 소수 사용자에게 먼저 제공해 반응 확인
