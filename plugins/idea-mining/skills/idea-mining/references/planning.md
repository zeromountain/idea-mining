# 기획 모드

발굴·검증까지 끝난 아이디어를 "그래서 뭘 어떻게 만들지"로 옮기는 단계다. 이 스킬의 나머지 부분은 전부 `~/ideas/`(저장소 밖, 홈 디렉토리)에만 쓰지만, 기획 모드는 유일하게 **사용자가 지금 작업 중인 프로젝트 폴더 안**에도 파일을 쓴다. 아이디어 파일 쪽 갱신은 계속 `~/ideas/`에 남는다.

전체 흐름: **0. 아이디어 선택 → 1. 컨텍스트 수집 → 2. 검증 게이트 → 3. 5단계 문서 순차 설계 → 4. 아이디어 파일 연동 → 5. 요약**

## 0단계: 아이디어 조회 및 선택

1. `~/ideas/INDEX.md`를 읽는다. 없으면 "아직 쌓인 아이디어가 없다"고 안내하고 발굴 모드로 전환할지 물어본다 (조회/관리 모드와 동일한 처리).
2. **관련도 순 정렬**: 현재 작업 폴더의 아래 정보를 아이디어와 대조한다.
   - 폴더명, `README.md`, `CLAUDE.md`, `package.json`/`pyproject.toml` 등의 `name`/`description`
   - 이미 존재하는 `docs/planning/*/01-prd.md`의 frontmatter `idea` 필드 (같은 아이디어로 기획을 이어가는 중인지 감지)
   - 각 아이디어의 `title` · `problem` · `domain`
3. `AskUserQuestion`으로 관련도 상위 3~4개를 제시한다. 관련 신호가 약하면 그 사실을 말하고 `INDEX.md` 전체를 상태별로 보여준 뒤 고르게 한다. 사용자가 이미 아이디어 ID나 파일을 특정했다면 이 단계는 건너뛴다.
4. 선택된 아이디어 파일 전문을 읽는다. 특히 `## 문제`, `## 해법 (선택된 것)`, `## 비평`, `## 검증 계획`, `## 실험 로그` — 이 다섯이 기획 문서의 원재료다.

## 1단계: 프로젝트 컨텍스트 수집 및 경로 확정

- 프로젝트 루트 = git 저장소 루트. 저장소가 아니면 현재 작업 디렉토리를 루트로 본다.
- 저장 경로 = `<프로젝트 루트>/docs/planning/<idea-slug>/`. `<idea-slug>`는 아이디어 `id`에서 날짜 접두사(`YYYY-MM-DD-`)를 뗀 값이다 — `INDEX.md`의 `ID` 컬럼과 동일한 값이므로 그대로 가져다 쓴다.
- 현재 위치가 프로젝트로 보이지 않으면(git 저장소도 아니고 `package.json`/`pyproject.toml`/`go.mod` 같은 프로젝트 표식도 없음) 경로를 임의로 만들지 말고 어디에 쓸지 사용자에게 묻는다.
- **이어쓰기 감지**: 해당 경로에 파일이 이미 있으면 절대 덮어쓰지 않는다. 어디까지 작성됐는지 보고하고 (a) 다음 단계부터 이어쓰기 (b) 특정 문서만 갱신 중 무엇을 할지 묻는다.
- 기존 코드베이스가 있으면 기술 스택·디렉토리 구조를 훑어 04·05단계 문서에 반영한다. 빈 폴더면 그린필드로 진행한다.

## 2단계: 검증 게이트 (막지 않고 경고)

아래 중 하나에 해당하면 3단계 진입 전에 반드시 짚어준다:

- `status: inbox`이고 실험 로그가 비어 있음 → "가장 위험한 가정(`<검증 계획의 가정 인용>`)이 아직 검증되지 않았다. 기획을 먼저 하면 그 가정 위에 문서를 쌓는 셈이다."
- `status: exploring`인데 실험 로그가 비어 있음 → 상태만 바뀌고 실제 검증은 없었다는 신호 (`portfolio.md`의 방치 감지와 같은 판정)
- kill 조건이 이미 충족된 것으로 보이는데 상태가 갱신되지 않음 → 먼저 상태 정리부터 제안

이건 게이트지 차단이 아니다 — 경고 후 사용자가 진행을 택하면 그대로 진행하되, **`01-prd.md` 상단에 "미검증 가정 위에서 시작한 기획"임을 명시**하고 어떤 가정이 미검증인지 적는다. 증거 등급을 항상 표기하는 이 스킬의 정직성 원칙(SKILL.md 품질 기준 2)의 연장이다.

## 3단계: 5단계 문서 순차 설계

문서를 하나 만들 때마다 사용자에게 보여주고 `AskUserQuestion`으로 **다음 단계로 갈지 / 이 문서를 고칠지 / 여기서 멈출지**를 묻는다. 중간에 멈춰도 그때까지 만든 문서는 그대로 유효한 산출물이다 — 5개를 다 채워야만 의미 있는 게 아니다.

| 순서 | 파일 | 내용 | 아이디어 파일에서 이어받는 것 |
|---|---|---|---|
| 1 | `01-prd.md` | 배경, 문제, 목표/비목표, 타깃 사용자, 성공 지표, 범위(MVP/제외), 리스크·미검증 가정 | `## 문제`의 5필드 → 배경·문제·타깃 / `## 검증 계획` → 리스크·성공 지표 |
| 2 | `02-features.md` | 기능 목록, 각 기능의 사용자 가치 · 우선순위(MVP/차기/보류) · 수용 기준 | `## 해법 (선택된 것)` → 기능 도출의 출발점 |
| 3 | `03-flows.md` | 핵심 사용자 플로우(텍스트 시퀀스), 화면·상태 목록, 엣지 케이스 | 02의 MVP 기능만 대상으로 한다 |
| 4 | `04-data-model.md` | 엔티티 · 필드 · 관계, 주요 상태 전이, 외부 연동 데이터 | 03의 플로우에서 필요한 데이터를 역산 |
| 5 | `05-tech-design.md` | 아키텍처 개요, 기술 선택과 근거, 주요 컴포넌트, 외부 의존성, 미해결 기술 리스크 | 기존 코드베이스가 있으면 그 스택을 우선 존중한다 |

품질 규칙 (발굴 워크플로의 기준을 그대로 승계한다):

- **구체성**: "사용자가 편해진다" 같은 주어 없는 서술은 통과시키지 않는다. 01의 타깃 사용자는 아이디어 파일의 "누가" 필드만큼 구체적이어야 한다.
- **정직성**: 아이디어 파일에서 근거가 E3(추론)뿐이던 항목을 기획 문서에서 사실처럼 단정하지 않는다 — `(미검증 가정)`으로 표시한다.
- **비평 승계**: 아이디어 파일 `## 비평`의 프리모템 · 레드팀 지적 중 아직 해소되지 않은 것은 `01-prd.md`의 리스크 섹션으로 반드시 옮긴다. 기획 문서를 쓰면서 조용히 사라지게 두지 않는다.
- **범위를 넓히지 않는다**: 아이디어 파일에 없던 기능을 새로 발명해 넣으려면 그게 신규 제안임을 명시하고 사용자 확인을 받는다.

모든 기획 문서의 frontmatter는 공통으로 `idea`(아이디어 id), `stage`(문서 번호/이름), `created`, `status`(`draft`/`reviewed`)를 갖는다. 실제 작성 예시는 `references/templates.md`를 참고한다.

## 4단계: 아이디어 파일 연동

`01-prd.md`가 만들어진 시점에 (5단계 전부가 끝나기를 기다리지 않는다) 아래 셋을 함께 처리한다:

1. **status 전이**: 아이디어 파일 frontmatter `status` → `building`. 2단계 경고 후 진행한 경우 이 전이도 함께 사용자 확인을 받는다.
2. **역링크**: 아이디어 파일의 `## 실험 로그`와 `## 재발견 / 새 근거` 사이에 `## 기획 문서` 섹션을 추가하고 프로젝트 경로 · 시작일 · 단계별 진행 상태를 적는다(`templates.md` 참고). 기획 문서 쪽 frontmatter의 `idea` 필드가 반대 방향 링크 역할을 한다.
3. **INDEX.md**: `기획` 컬럼을 추가하고(없으면 `—`) 해당 행을 `building` 표로 옮긴다. `killed` 표는 기존 컬럼 구조를 유지하되, 기획까지 갔던 항목이 죽으면 `사유` 뒤에 기획 문서 경로를 괄호로 남긴다.

이후 문서(02~05)를 이어서 만들 때마다 아이디어 파일의 `## 기획 문서` 진행 상태 표만 갱신하면 된다 — status·INDEX 갱신은 01 생성 시 한 번이면 충분하다.

## 5단계: 요약

생성된 파일 경로 전부, 각 문서의 상태(작성됨/미작성), 아이디어 파일 상태 변화, 그리고 **다음 행동**(미검증 가정이 남아 있으면 그 검증부터, 아니면 `05-tech-design.md` 기준 첫 구현 작업)을 요약해 알려준다.
