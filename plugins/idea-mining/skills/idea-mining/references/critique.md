# 비평 (죽이기 단계)

3단계 수렴에서 점수를 매기기 **전에** 이 단계를 거친다. 아이디어를 낸 사람이 그대로 채점까지 하면 점수가 후하게 나오기 마련이라, 채점 전에 최대한 세게 반박하는 절차를 먼저 넣는다.

## 1. 프리모템 (사전 부검)

"6개월 뒤 이 아이디어는 실패했다"고 **단정**하고, 왜 실패했는지 부검 보고서를 쓴다. "어떤 리스크가 있을까"라고 미래형으로 물으면 두루뭉술한 답이 나오지만, 실패를 이미 벌어진 일로 놓고 원인을 캐물으면 훨씬 구체적인 답이 나온다.

각 아이디어마다 실패 원인을 5개 뽑는다. 뻔한 것 하나로 끝내지 말고, 도메인 파일의 "흔한 실패 패턴"을 참고해 그 도메인에서 실제로 반복되는 실패 유형을 우선 점검한다.

빠른 모드는 레드팀 없이 이 프리모템 결과만으로 3번 반영 규칙을 적용한다. 이때도 §2에서 레드팀에게 요구하는 것과 같은 분류(구조적/완화 가능)를 스스로 매긴다 — 안 그러면 "실패 원인 5개를 뽑으라"는 지시 자체가 전부 치명적으로 들리는 방향으로 쏠리기 쉽다.

마지막으로 **이 형태가 4단계 이후의 최소 검증 실험을 통과할 확신도를 상/중/하로 매긴다.** 이 확신도가 §3 반영 규칙의 피벗 루프를 언제 멈출지 판단하는 기준이다.

## 2. 독립 레드팀 (서브에이전트, 깊은 모드)

빠른 모드에서는 생략한다(가벼움이 목적이므로). 깊은 모드에서는 아이디어당 서브에이전트를 하나 띄워 반박을 맡긴다.

**맥락 차단이 핵심이다**: 서브에이전트에게 이 아이디어가 어떻게 나왔는지(어떤 문제에서 출발했는지, 어떤 논리로 도출됐는지)는 넘기지 않는다. 생성 과정의 논리를 보여주면 그 논리에 설득당해서 반박이 약해진다. 넘기는 것은 다음 셋뿐이다:

1. 아이디어 한 줄 요약
2. 풀려는 문제 정의 (5필드)
3. 해당 도메인의 "흔한 실패 패턴" 체크리스트 (`domains/<domain>.md`)

프롬프트 지시는 명확하게 "이 아이디어를 옹호하지 말고 죽여라. 왜 실패할지, 어떤 전제가 틀렸을 가능성이 있는지 최대한 찾아라"로 준다. 우호적인 톤으로 물으면 형식적인 반박만 돌아온다. **주장마다 E1/E2/E3(증거 등급, `evidence.md` 참고)를 표기하라고 함께 지시한다** — 서브에이전트도 근거 없는 단정을 그럴듯하게 낼 수 있고, 그 단정이 틀린 채로 아이디어를 죽이면 검증 없이 반박한 셈이 되기 때문이다.

**동시에 반박마다 "구조적"인지 "완화 가능"인지 스스로 분류하게 지시한다** — 구조적은 가정을 어떻게 바꿔도 못 살리는 경우(법적으로 불가능, 시장 자체가 없음이 확인됨 등), 완화 가능은 가정 A를 B로 바꾸거나 대상을 좁히면 해소되는 경우다. 완화 가능으로 분류할 땐 어떻게 바꾸면 해소되는지 한 줄로 같이 쓰게 한다. "죽여라"라는 지시는 반박을 찾는 동기를 세게 유지하기 위한 것이지, 찾은 반박을 전부 구조적 실패로 몰아가라는 뜻이 아니다 — 이 분류 지시를 빼면 서브에이전트가 "어렵다"와 "불가능하다"를 구분하지 않고 전부 치명적으로 보고하는 경향이 생기고, 그 결과 아이디어가 필요 이상으로 자주 killed 처리된다.

**마지막으로 이 아이디어(또는 피벗된 형태)가 검증을 통과할 확신도를 상/중/하로 매기게 지시한다** — 반박 개수나 강도가 아니라 "이 형태로 최소 검증 실험을 돌리면 살아남을 것 같은가"를 기준으로. 이 확신도는 §3 피벗 루프의 종료 신호로 쓰인다.

## 3. 반영 규칙 (피벗 루프)

레드팀·프리모템 결과를 1회성 판정으로 끝내지 않고, **확신도가 "상"에 도달하거나 피벗 라운드 상한(3회)에 닿을 때까지 반복한다.** (이 "피벗 라운드"는 §5의 "발굴 라운드"—문제 선택부터 비평까지 한 바퀴—와는 다른 단위다. 여기서는 같은 아이디어 하나를 놓고 반박↔수정을 반복하는 안쪽 루프를 가리킨다.) 이전엔 구제 시도를 반박당 1회로 제한했는데, 그러면 첫 피벗이 부족한 아이디어가 곧바로 killed되거나 확신도 "중/하"인 채로 다음 단계로 넘어가는 문제가 있었다 — 아이디어 자체의 결함인지 아직 덜 다듬어진 것뿐인지 구분할 기회를 한 번 더 준다.

**피벗 라운드 1회**는 아래 순서로 진행한다:

1. **관문 1 (근거)**: 이번 라운드에서 나온 반박마다, 근거가 E3(추론)뿐이면 그대로 두지 않는다 — 검색 1회로 E1/E2로 승격시켜 본다. 승격에 실패하면(원 자료를 못 찾거나 사실이 아닌 것으로 확인되면) 그 반박은 무효로 처리한다. 검증 대상은 "이 사실이 틀리면 판정 자체가 바뀌는 주장"으로 한정한다. 이 과정(주장 → 검증 결과)은 검증 여부와 무관하게 아이디어 파일 또는 세션 로그에 기록한다.
2. **관문 2 (구조 판정)**: 관문 1을 통과한 반박 중 "구조적"으로 분류된 것이 하나라도 있으면 **그 즉시 killed로 확정하고 피벗 루프를 종료한다** — 구조적 반박(법적 불가능, 확인된 시장 부재 등)은 라운드를 더 돌려도 못 살리는 것이므로 반복은 낭비다.
   - killed로 확정되면 **정식 아이디어 파일을 만들지 않는다.** 세션 로그에 문제·해법·비평 전체(몇 피벗 라운드를 거쳤는지 포함)를 남기고, `~/ideas/INDEX.md`의 killed 표에 제목·영역·킬 사유·세션 로그 링크만 한 줄 추가한다 (`portfolio.md`, `templates.md` 참고). 이건 저장 이후 kill 조건 충족으로 죽는 경우(`portfolio.md`의 `exploring → killed`, 파일이 이미 있고 상태만 바뀜)와는 다른 경로다.
3. **구제 시도**: 구조적 반박이 없으면, 남은 "완화 가능" 반박들을 가정 변경·세그먼트 축소로 해소한다 ("이 반박이 사실이어도 대상을 OO로 좁히거나 XX를 바꾸면 여전히 성립하는가"). 수정한 가정과 새 형태를 1줄로 기록한다. **형태가 실질적으로 바뀌었다면(예: 별도 도구 → 기존 워크플로에 얹는 가벼운 형태로 전환)**, `evidence.md`의 문제 공간 지도 대조를 다시 한다 — 피벗된 형태도 이미 존재할 수 있기 때문이다.
4. **재비평**: 수정된 형태를 다시 비평한다 (빠른 모드는 프리모템 재실행, 깊은 모드는 레드팀 서브에이전트 재실행 — 이전 반박이 아니라 수정된 형태 전체를 새로 검토하게 한다). 새 피벗 라운드에서 이전엔 안 보이던 반박이나 구조적 문제가 드러날 수 있다 — 그러면 2번부터 다시 적용한다.
5. **확신도 확인**: 이번 피벗 라운드의 확신도가 "상"이면 루프를 종료하고 4단계(점수 매기기)로 넘어간다. "중/하"면 1번부터 다음 피벗 라운드를 시작한다.

**피벗 라운드 상한은 3회다.** 3회를 다 돌았는데도 확신도가 "상"에 도달하지 못하면 자동으로 killed 처리하거나 그대로 저장하지 않는다 — 이 시점에서 부족한 게 아이디어의 본질적 결함인지, 아니면 검증 전이라 원래 확신하기 어려운 것뿐인지 모델 혼자 구분하기 어렵기 때문이다. 대신 마지막 라운드의 형태·확신도·남은 리스크를 정리해 `AskUserQuestion`으로 사용자에게 묻는다:
1. 이 확신도로 그대로 저장한다 (남은 리스크를 아이디어 파일에 명시)
2. 피벗 라운드를 더 진행한다 (몇 회 더 할지 다시 묻는다)
3. killed로 처리한다

**견딤** (첫 피벗 라운드부터 반박이 없거나 확신도가 곧바로 "상")이면 루프 없이 바로 4단계로 넘어간다.

## 4. 강제 순위 (자기채점 편향 완화)

절대 점수(`scoring.md`의 25점 만점)만 쓰면 여러 후보가 전부 후하게 나오는 경향이 있다. 절대 점수와 별개로, 후보들을 서로 비교해 **순위**를 매긴다 ("A가 B보다 나은 이유는..."). 순위는 상대 비교라 절대 점수보다 왜곡이 적다. 최종 저장 여부(체크포인트 B)를 정할 때 점수와 순위를 함께 참고한다.

필터를 세게 통과한 결과 후보가 1개만 남을 수 있다 — 이 경우 "유일 생존 후보"라고만 적지 않는다. 대신 **탈락한 다른 후보들 대비 왜 이것만 살아남았는지 1줄** + **`~/ideas/INDEX.md`의 기존 아이디어들과 비교했을 때 이게 어디쯤 있는지 1줄**로 대체한다.

## 5. 라운드 전멸 가드

모드에 관계없이 한 발굴 라운드(발산 → 사전 조사 → 비평, §3의 피벗 루프까지 포함)를 거쳤는데 후보가 하나도 안 남으면(전부 killed), 다음 문제로 그냥 넘어가지 말고 즉시 `AskUserQuestion`으로 묻는다:

1. **같은 문제, 발산 각도를 바꿔서 재시도** — 특히 이번 라운드에서 안 쓴 `divergence.md` 기법 위주로
2. **체크포인트 A에서 골랐던 다른 문제로**
3. **영역 자체를 전환**
4. **제약을 완화** — 0단계에서 정한 제약(예산·시간·인력 등)이 탈락의 직접 원인이었는지 점검하고, 사용자가 그 제약을 풀 의향이 있는지 묻는다. 실제로 전멸의 원인이 아이디어 자체가 아니라 제약과의 충돌인 경우가 있다 — 이 선택지를 건너뛰지 않는다.

**빠른 모드에서 전멸하면 다섯 번째 선택지를 추가한다**: 깊은 모드로 전환해서 독립 레드팀·증거 승격까지 거쳐 다시 판정해볼지. 빠른 모드는 서브에이전트 반박이나 근거 검증 없이 프리모템(본인 판단)만으로 전멸했을 수 있어서, 정말 가망이 없는 건지 판정 자체가 얕았던 건지 구분이 안 된 상태이기 때문이다.

"그냥 알아서 진행해" 모드에서는 1번(발산 각도 변경)을 자동으로 1회 시도하고, 그래도 전멸하면 결과와 이유를 보고한 뒤 멈춘다 — 사용자 확인 없이 영역을 임의로 계속 바꾸지 않는다.
