# 비평 (죽이기 단계)

3단계 수렴에서 점수를 매기기 **전에** 이 단계를 거친다. 아이디어를 낸 사람이 그대로 채점까지 하면 점수가 후하게 나오기 마련이라, 채점 전에 최대한 세게 반박하는 절차를 먼저 넣는다.

## 1. 프리모템 (사전 부검)

"6개월 뒤 이 아이디어는 실패했다"고 **단정**하고, 왜 실패했는지 부검 보고서를 쓴다. "어떤 리스크가 있을까"라고 미래형으로 물으면 두루뭉술한 답이 나오지만, 실패를 이미 벌어진 일로 놓고 원인을 캐물으면 훨씬 구체적인 답이 나온다.

각 아이디어마다 실패 원인을 5개 뽑는다. 뻔한 것 하나로 끝내지 말고, 도메인 파일의 "흔한 실패 패턴"을 참고해 그 도메인에서 실제로 반복되는 실패 유형을 우선 점검한다.

## 2. 독립 레드팀 (서브에이전트, 깊은 모드)

빠른 모드에서는 생략한다(가벼움이 목적이므로). 깊은 모드에서는 아이디어당 서브에이전트를 하나 띄워 반박을 맡긴다.

**맥락 차단이 핵심이다**: 서브에이전트에게 이 아이디어가 어떻게 나왔는지(어떤 문제에서 출발했는지, 어떤 논리로 도출됐는지)는 넘기지 않는다. 생성 과정의 논리를 보여주면 그 논리에 설득당해서 반박이 약해진다. 넘기는 것은 다음 셋뿐이다:

1. 아이디어 한 줄 요약
2. 풀려는 문제 정의 (5필드)
3. 해당 도메인의 "흔한 실패 패턴" 체크리스트 (`domains/<domain>.md`)

프롬프트 지시는 명확하게 "이 아이디어를 옹호하지 말고 죽여라. 왜 실패할지, 어떤 전제가 틀렸을 가능성이 있는지 최대한 찾아라"로 준다. 우호적인 톤으로 물으면 형식적인 반박만 돌아온다. **주장마다 E1/E2/E3(증거 등급, `evidence.md` 참고)를 표기하라고 함께 지시한다** — 서브에이전트도 근거 없는 단정을 그럴듯하게 낼 수 있고, 그 단정이 틀린 채로 아이디어를 죽이면 검증 없이 반박한 셈이 되기 때문이다.

## 3. 반영 규칙

레드팀·프리모템 결과를 세 갈래로 처리한다:

- **치명적**: 핵심 전제가 무너지는 반박이면 killed로 처리한다. **단, 반박의 근거가 E3(추론)뿐이면 그대로 치명적으로 확정하지 않는다** — 검색 1회로 그 주장을 E1/E2로 승격시켜 본다. 승격되면 치명적으로 확정하고, 승격에 실패하면(원 자료를 못 찾거나 사실이 아닌 것으로 확인되면) 부분적으로 강등해서 처리한다. 검증 대상은 "이 사실이 틀리면 판정 자체가 바뀌는 주장"으로 한정한다 — 레드팀 답변 전체를 매번 검색으로 되짚을 필요는 없다. 이 과정(레드팀 주장 → 검증 결과)은 검증 여부와 무관하게 아이디어 파일 또는 세션 로그에 반드시 기록한다.
  - killed로 확정되면 **정식 아이디어 파일을 만들지 않는다.** 세션 로그에 문제·해법·비평 전체를 남기고, `~/ideas/INDEX.md`의 killed 표에 제목·영역·킬 사유·세션 로그 링크만 한 줄 추가한다 (`portfolio.md`, `templates.md` 참고). 이건 저장 이후 kill 조건 충족으로 죽는 경우(`portfolio.md`의 `exploring → killed`, 파일이 이미 있고 상태만 바뀜)와는 다른 경로다 — 둘을 혼동하지 않는다.
- **부분적**: 가정을 수정하면 살아남는 반박이면, 가정을 고치고 다음 단계(점수 매기기)로 넘어간다. 수정한 가정은 문서에 남긴다. **반박으로 해법의 형태가 실질적으로 바뀌었다면(예: 별도 도구 → 기존 워크플로에 얹는 가벼운 형태로 전환)**, 그 새 형태에 대해 `evidence.md`의 문제 공간 지도 대조를 다시 한 뒤에 점수를 매긴다 — 피벗된 형태도 이미 존재할 수 있기 때문이다. 원래 형태와 피벗 사유를 1줄로 남긴다.
- **견딤**: 반박에도 근거가 흔들리지 않으면 점수에 긍정적으로 반영해도 된다 — 검증을 거친 아이디어라는 뜻이다.

## 4. 강제 순위 (자기채점 편향 완화)

절대 점수(`scoring.md`의 25점 만점)만 쓰면 여러 후보가 전부 후하게 나오는 경향이 있다. 절대 점수와 별개로, 후보들을 서로 비교해 **순위**를 매긴다 ("A가 B보다 나은 이유는..."). 순위는 상대 비교라 절대 점수보다 왜곡이 적다. 최종 저장 여부(체크포인트 B)를 정할 때 점수와 순위를 함께 참고한다.

필터를 세게 통과한 결과 후보가 1개만 남을 수 있다 — 이 경우 "유일 생존 후보"라고만 적지 않는다. 대신 **탈락한 다른 후보들 대비 왜 이것만 살아남았는지 1줄** + **`~/ideas/INDEX.md`의 기존 아이디어들과 비교했을 때 이게 어디쯤 있는지 1줄**로 대체한다.

## 5. 라운드 전멸 가드

깊은 모드에서 한 라운드(발산 → 사전 조사 → 비평)를 거쳤는데 후보가 하나도 안 남으면, 다음 문제로 그냥 넘어가지 말고 즉시 `AskUserQuestion`으로 묻는다:

1. **같은 문제, 발산 각도를 바꿔서 재시도** — 특히 이번 라운드에서 안 쓴 `divergence.md` 기법 위주로
2. **체크포인트 A에서 골랐던 다른 문제로**
3. **영역 자체를 전환**
4. **제약을 완화** — 0단계에서 정한 제약(예산·시간·인력 등)이 탈락의 직접 원인이었는지 점검하고, 사용자가 그 제약을 풀 의향이 있는지 묻는다. 실제로 전멸의 원인이 아이디어 자체가 아니라 제약과의 충돌인 경우가 있다 — 이 선택지를 건너뛰지 않는다.

"그냥 알아서 진행해" 모드에서는 1번(발산 각도 변경)을 자동으로 1회 시도하고, 그래도 전멸하면 결과와 이유를 보고한 뒤 멈춘다 — 사용자 확인 없이 영역을 임의로 계속 바꾸지 않는다.
